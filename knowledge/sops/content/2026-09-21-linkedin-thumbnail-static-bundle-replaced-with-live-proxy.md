# SOP: LinkedIn Image Thumbnails — Replaced Stale Git-Bundle Serving With a Live Backend Proxy
Date: 2026-09-21
Product: ceo-dashboard's LinkedIn Content review panel + Cloud Decoded FastAPI backend
Status: Live — real root cause fixed, tested, deployed

---

## What triggered this

Immediately after [[2026-09-21-linkedin-image-generation-moved-back-to-draft-time]] shipped, Kelvin sent a screenshot: posts in the review queue now had real `image_brief` paths, but every thumbnail showed red "image failed to load" text. His message:

> "go back to previous iterations and figure out what was working before you implemented all of these changes that were outside the scope of what I asked. images are still not pulling up"

## Root cause — pre-existing, not introduced by the same-session image-timing fix

`ceo-dashboard/app/api/asset/[...path]/route.ts` did not read image bytes live. It read them from a **git-committed snapshot** of `assets_library/my_originals/` that `next.config.ts`'s `outputFileTracingIncludes` bakes into the Vercel deployment's serverless function at build time — a workaround from commit `f88e775` (2026-07-24), written explicitly because the FastAPI backend "had never been deployed anywhere reachable" at that time.

The backend has been live on Railway since before 2026-09-16 (`generate_linkedin_queue_images`'s own docstring, added that day, calls it "live... now"), making the July workaround both obsolete and silently broken ever since: **any image generated by a live backend run — at draft time or the old approval time, it made no difference — was never committed to git**, so it was never bundled into ceo-dashboard's next Vercel build. Only the 107 files from the 2026-09-15 backlog-repair script (committed directly, by hand, as part of that session's fix) ever actually rendered. Every image generated by a real production run since then has 404'd in the dashboard.

This bug predates and is unrelated to the same-session image-timing revert. It was invisible before that fix only because pending_review rows never had an image to try to load — the same "image failed to load" would have hit any approved/published row's thumbnail too, if anyone had looked closely at one generated after 2026-09-15.

## Fix

Restored the original, correct architecture (the one `f88e775`'s own commit message describes replacing, back when it was the only option) now that its precondition — a reachable backend — is true:

- `api/routes/internal_marketing.py`'s `GET /internal/marketing/assets/{path}` (`get_asset`) already read live off the backend's own filesystem and was already correct — it was simply never called (dead code since July). Changed its auth from `get_internal_user` (Bearer token, meant for a hypothetical direct browser call that never existed) to `require_marketing_api_key` — the same server-to-server shared secret this file's sibling bridge endpoint (`generate_linkedin_queue_images`) already uses — since the only caller is now ceo-dashboard's own Next.js route handler, not a browser.
- `ceo-dashboard/app/api/asset/[...path]/route.ts` rewritten to proxy: keeps its existing `requireRole(["admin", "marketing"])` session check, then calls the live backend with `X-API-Key: MARKETING_API_KEY` (identical pattern to `app/api/linkedin-queue/generate/route.ts`'s "Fire posts now" proxy) and streams the response back.
- `next.config.ts`'s `outputFileTracingIncludes` hack removed entirely — no longer needed, and actively wrong to keep (it would keep serving stale/missing images even after this fix if left in place, since Next.js would still try to trace and bundle a folder that no longer needs bundling).
- No client-side change needed — `AssetThumbnail.tsx` and `fetchAssetBlobUrl` already call the same-origin `/api/asset/...` path; only what's behind it changed.

The 107 already-committed PNGs under `assets_library/my_originals/` in git were left in place (harmless, not the active serving path anymore, not worth a separate cleanup pass this session).

## Test coverage

- `tests/test_internal_marketing_publish.py`'s three existing `get_asset` tests (serves a real file / 404s on missing / blocks path traversal) updated to drop the now-removed `user=` kwarg — behavior unchanged, they call the function directly.
- No new backend tests needed — the auth dependency swap itself has no independent logic to test beyond what `require_marketing_api_key` already covers elsewhere.
- `ceo-dashboard`: `tsc --noEmit` clean outside the pre-existing, untracked `ThdConsulting*` files (confirmed unrelated — untracked since before this session, not part of this commit, and never reach Vercel's build since Vercel builds from git). `npm run build` fails locally only because those untracked files exist on local disk; the actual deploy is unaffected.
- Full backend suite: 1998 passed, same 4 pre-existing unrelated failures as every prior run this session.

## If this breaks again

- **"image failed to load" reappears:** first check whether `ceo-dashboard/app/api/asset/[...path]/route.ts` is still proxying to the live backend (`NEXT_PUBLIC_API_URL` + `MARKETING_API_KEY`) rather than reading local/bundled files again — don't reintroduce `outputFileTracingIncludes`.
- **The backend itself becomes unreachable again** (Railway outage, wrong `NEXT_PUBLIC_API_URL`): the route now returns a 503 naming the unreachable URL instead of a silent 404 — check that message first.
- **`MARKETING_API_KEY` missing on ceo-dashboard's Vercel deployment:** the route now returns a clear 500 saying so, rather than a confusing generic failure.
